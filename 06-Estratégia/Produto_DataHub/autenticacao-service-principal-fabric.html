01 · O Problema

Por que a credencial pessoal quebra os modelos

Hoje, cada modelo semântico do workspace está configurado com uma conta de usuário pessoal (OAuth 2.0) como credencial da fonte de dados. Isso funciona no dia a dia, mas cria uma dependência frágil e invisível.

Quando um modelo semântico precisa atualizar os dados no serviço do Power BI, ele usa a credencial salva para se autenticar na fonte (no nosso caso, o SQL Endpoint do Lakehouse no Fabric). Se essa credencial é uma conta pessoal:

Senha expiraou MFA muda
→
Token inválidorefresh falha
→
Erro no serviço"artefato sem detalhes de conexão"
→
Painel quebradopara todos os usuários

Esse é exatamente o padrão do erro DMTS_EntityNotFoundOrUnauthorized visto nos modelos de Santos e Osasco — e confirmado como um problema generalizado em todos os modelos semânticos do ambiente, não um caso isolado.

Risco adicional

Se a pessoa dona da credencial sair da empresa, tiver o acesso revogado ou simplesmente trocar de senha sem avisar, todos os modelos que dependem dela param de atualizar ao mesmo tempo — sem aviso prévio até o próximo refresh agendado falhar.

02 · Fundamentos

Tipos de autenticação disponíveis no Fabric

Ao configurar uma conexão de dados no Power BI/Fabric (seja no gateway, seja em uma conexão de nuvem), estes são os métodos de autenticação suportados. Nem todos se aplicam a toda fonte — para o SQL Analytics Endpoint de um Lakehouse, os relevantes são OAuth2 e Service Principal.

👤

OAuth 2.0 (conta pessoal)

Usa a identidade Microsoft Entra ID de um usuário real, com login interativo (Organizational Account).

Situação atual do ambiente
🤖

Service Principal

Identidade não humana (app registration no Entra ID), autenticada via Client ID + Tenant ID + Client Secret/certificado.

Recomendado para produção
🪟

Windows

Usa credenciais de domínio Windows. Aplicável principalmente a fontes on-premises via gateway.

Não se aplica ao Fabric
🔑

Basic (usuário/senha)

Usuário e senha simples do próprio banco de dados. Comum em SQL Server on-premises, IBM DB2, MySQL etc.

Não suportado por SQL Endpoint Fabric
🗝️

Key (chave de API)

Uma chave/token estático fornecido pela fonte, sem envolver identidade de usuário.

Usado em Azure Table Storage, APIs
🌐

Anonymous

Sem autenticação — a fonte é pública ou não exige credenciais.

Não aplicável a dados corporativos
Sobre Direct Lake

Segundo a documentação oficial de segurança do Direct Lake, apenas OAuth 2.0, Service Principal e Workspace Identity são suportados como método de autenticação — chave ou SAS aparecem na interface mas não funcionam para esse modo de conexão.

03 · Comparação direta

OAuth pessoal vs. Service Principal

Critério OAuth 2.0 pessoal Service Principal
Estabilidade do token Expira, exige reautenticação; qualquer bloqueio de MFA ou política de senha derruba a conexão. Frágil Renovado automaticamente via client credentials flow; segredo válido por período definido (ex: 6, 12, 24 meses). Estável
Dependência de pessoa Atrelado a um funcionário específico — sai da empresa, muda de time ou perde acesso, o modelo quebra. Alto risco Identidade da aplicação, independente de qualquer colaborador. Sem dependência humana
Reuso entre modelos Cada modelo geralmente fica com a conta de quem publicou por último. Fragmentado Uma única conexão de nuvem pode ser compartilhada por todos os modelos do workspace. Centralizado
Auditoria e governança Difícil rastrear "de quem é essa credencial" meses depois. Opaco Identidade nomeada e documentada no Entra ID, com escopo de permissão explícito. Rastreável
Automação (CI/CD) Não recomendado — exige login interativo. Manual Padrão recomendado pela Microsoft para pipelines, scripts e deploys automatizados. Nativo
Configuração inicial Simples — só fazer login. Rápido Exige criar App Registration, habilitar tenant setting, dar acesso a workspace e fontes. Mais trabalho no início
Row-Level Security (RLS/OLS) Suporta normalmente. OK Service Principals não podem ser usados como membros de role de RLS/OLS. Limitação conhecida
04 · Balanço

Vantagens e desvantagens do Service Principal

✔ Vantagens

  • Elimina a causa raiz do erro recorrente de "artefato sem detalhes de conexão" causado por troca/expiração de senha pessoal.
  • Uma única conexão compartilhada pode alimentar todos os modelos semânticos do workspace — corrige o problema uma vez, não modelo a modelo.
  • Segue a prática recomendada oficial da Microsoft para cenários de CI/CD e reuso de conexão entre ambientes (Dev/Test/Prod).
  • Permissões de acesso à fonte ficam explícitas e documentadas (App Registration nomeado), facilitando auditoria.
  • Não depende de nenhum colaborador específico continuar na empresa ou manter a mesma senha.

✘ Desvantagens / Cuidados

  • Exige acesso ao Entra ID (Azure AD) para criar/gerenciar o App Registration — normalmente depende de um administrador.
  • O client secret expira (recomendação: renovar a cada 30 dias segundo boas práticas do Fabric Data Warehouse, ou usar certificado/credencial federada para evitar rotação manual).
  • Precisa que o tenant admin habilite "Service principals can call Fabric public APIs" — é uma configuração de todo o tenant, então deve ser feita com cuidado (idealmente restrita a um grupo de segurança específico).
  • Não suporta Row-Level Security/Object-Level Security como identidade de usuário.
  • Setup inicial tem mais passos que simplesmente "fazer login".
05 · Passo a passo

Processo de migração para o nosso ambiente

Sequência recomendada para o workspace Acto Cidade Inteligente, reaproveitando o Service Principal já usado na migração de Osasco/Santos.

Entra ID admin

Confirmar ou criar o Service Principal

Verificar se PowerBIDatasets_acto_svc já existe em Entra ID → App registrations. Se sim, coletar:

  • Application (client) ID
  • Directory (tenant) ID
  • Client secret válido (gerar um novo em "Certificates & secrets" se estiver expirado ou perdido)

Se não existir, criar um novo App Registration com "Accounts in this organizational directory only".

Fabric tenant admin

Habilitar Service Principals no tenant

No Admin Portal do Fabric → Configurações do tenant → Developer settings, habilitar "Service principals can call Fabric public APIs", preferencialmente restringindo a um grupo de segurança específico (recomendado pela Microsoft) em vez de liberar para toda a organização.

Admin do workspace

Dar acesso do SP ao workspace

No workspace (bis_obras_producao e demais afetados) → Gerenciar acesso → Adicionar pessoas ou grupos → buscar pelo nome do App Registration → atribuir papel Membro ou Contribuidor.

Admin do Lakehouse

Conceder acesso de leitura aos dados

No Lakehouse de origem (lh_solicitacoes_acto, lh_cidade_inteligente_osasco, etc.) → conceder ao SP no mínimo:

  • Read — acesso ao artefato
  • Read all data using SQL (ReadData) — necessário para consultas via SQL Endpoint
Você / qualquer membro com acesso

Criar a conexão de nuvem compartilhada

Em Configurações (engrenagem) → Gerenciar conexões e gateways → Novo → Cloud:

  • Tipo de conexão: SQL Server (ou "Power BI Semantic Model", conforme o caso)
  • Servidor: o SQL Analytics Endpoint do Lakehouse
  • Método de autenticação: Service Principal
  • Preencher Tenant ID, Service Principal ID (client ID) e Service Principal Key (client secret)

Nomear de forma clara, por exemplo conn_sp_acto_svc_lh_solicitacoes, e garantir que o workspace/usuários certos tenham permissão de uso dessa conexão.

Você

Remapear cada modelo semântico

Para cada modelo afetado: Configurações do modelo → Conexões de gateway e nuvem → trocar o mapeamento da conexão pessoal atual pela nova conexão com Service Principal → Aplicar → rodar refresh manual para validar.

Atenção ao expirar

Documente a data de expiração do client secret e agende sua renovação com antecedência — um secret expirado gera exatamente o mesmo tipo de falha que estamos corrigindo agora, só que em todos os modelos migrados de uma vez.

06 · Acompanhamento

Checklist de migração

  • Service Principal PowerBIDatasets_acto_svc confirmado, com Client ID / Tenant ID / Secret válidos em mãos
  • "Service principals can call Fabric public APIs" habilitado no tenant (restrito a grupo de segurança)
  • SP adicionado como Membro/Contribuidor nos workspaces relevantes
  • SP com permissão de leitura (Read + ReadData) em cada Lakehouse de origem
  • Conexão de nuvem compartilhada criada com autenticação Service Principal
  • Modelo pbi_obras_santos_seont_acomp_analistas remapeado e testado (piloto)
  • Demais modelos do workspace remapeados um a um
  • Data de expiração do client secret documentada e lembrete de renovação criado
